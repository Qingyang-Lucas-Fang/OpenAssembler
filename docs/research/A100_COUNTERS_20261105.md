# Current A100 Counter Replay

Date: 2026-11-05. Device: NVIDIA A100-SXM4-40GB, SM80, 108 SMs, driver
13030, reported clock 1.41 GHz. The isolated harness is
[`exp/a100_counters/run.py`](../../exp/a100_counters/run.py); raw output is
[`counter-validation_20261105T164620.918665Z.json`](../../exp/a100_counters/counter-validation_20261105T164620.918665Z.json).

The counter runs compared current archived OpenAssembler `m_fast`, corrected `morton8`
and ptxas cubins for the tall 16384x4096x4096 shape at identical grid 128x32,
128 threads and 64 KiB dynamic shared memory. Every candidate passed zero,
integer and normal full-output checks, ptxas bitwise checks, canaries and the
FP32 reference tolerance before timing/profile replay. The cuBLAS control was
added after the first two counter runs and is recorded separately below.

## Results

Timing medians are nine shuffled CUDA-graph samples and are not mixed with NCU
replay time. NCU ran with unmodified clocks (`--clock-control none`); replay
can perturb caches.

| Candidate | OA graph ms | ptxas graph ms | OA NCU ms | ptxas NCU ms |
|---|---:|---:|---:|---:|
| Tall FP16 `m_fast` | 2.675 | 3.551 | 2.997 | 3.478 |
| Tall FP16 `morton8` | 2.535 | 2.377 | 2.774 | 2.633 |
| Tall BF16 `m_fast` | 2.610 | 3.506 | 2.731 | 3.562 |
| Tall BF16 `morton8` | 2.475 | 2.320 | 2.236 | 2.668 |

The m_fast ptxas replay is substantially slower than the earlier archived
validation sample, while Morton ptxas values are close. This shows that small
graph timing is sensitive to worker state; the m_fast/ptxas ratio needs repeat
runs before promotion decisions. NCU values are replay measurements, not graph
timing replacements.

## Interpretation

1. **Tensor Core count is not the gap.** OA and ptxas issue the same number of
   Tensor Core instructions. Static HMMA count cannot explain the result.
2. **OA has a repeatable short-scoreboard/wait signature.** OA short-scoreboard
   stalls are about 9.5-10.1% versus 1.1-2.1% for ptxas, and OA wait stalls
   are about 46.6-50.6% versus 24.3-37.7%. This is consistent with extra
   scalar/address/dependency work or a less effective issue schedule. It does
   not prove register-bank or operand-collector causality.
3. **Long scoreboard is not uniformly worse for OA.** ptxas m_fast has much
   higher long-scoreboard stalls, while Morton reduces both methods' long
   scoreboard values. The OA deficit is not simply global-memory latency.
4. **CTA order changes locality.** OA Morton raises L2 hit rate from about
   62.5-63.8% to 84.9-85.0% and reduces shared-load bank conflicts. It also
   improves OA graph time versus OA m_fast. The ptxas Morton replay has higher
   Tensor activity and lower scoreboard stalls, so CTA order does not remove
   the ptxas scheduling advantage.
5. **Bank conflicts are a secondary signal.** OA m_fast has more conflicts than
   ptxas in FP16 but fewer in BF16; Morton OA reduces them strongly. Because
   conflict counts and timing move differently across methods, conflict count
   alone cannot identify the bottleneck.

## Repeat Graph and Counter Run

The repeat used the same cubin hashes, inputs, launch geometry and nine shuffled
graph samples. Its medians were:

| Candidate | OA graph ms | ptxas graph ms |
|---|---:|---:|
| Tall FP16 `m_fast` | 2.667 | 3.551 |
| Tall FP16 `morton8` | 2.482 | 2.327 |
| Tall BF16 `m_fast` | 2.608 | 3.512 |
| Tall BF16 `morton8` | 2.422 | 2.267 |

Within this run, timing samples were tight: OA coefficients of variation were
about 0.5-0.7%, and ptxas about 0.1-0.4%. The two `m_fast` ptxas medians still
differed from the first run, so the result is worker/run-state sensitive and
should not be used as a cuBLAS comparison or as a production promotion gate.
The Morton OA/ptxas relationship was stable across the two runs.

The repeat NCU replay reproduced the relative signatures while changing some
absolute values:

All methods again executed 134,217,728 Tensor Core instructions. Morton reduced
OA DRAM bytes from roughly 3.15-3.26 GB to 1.08 GB in this replay, alongside
the L2-hit increase. This supports CTA locality as an OA improvement for this
shape. One NCU replay per case is not enough to establish counter repeatability
or causality. Neither profile isolates operand-collector pressure, so that
remains an open hypothesis.

## Three-Way cuBLAS Control

The corrected isolated mode, `--mode validate-cublas`, uses explicit ctypes
signatures, dtype-matched `CUDA_R_16F`/`CUDA_R_16BF`, an explicit stream and
CUDA events. It checks cuBLAS against the FP32 reference before timing. The
`--mode validate-cublas-ncu` run adds NCU replay for all three paths; raw output
is [`counter-validation_20261105T172129.284610Z.json`](../../exp/a100_counters/counter-validation_20261105T172129.284610Z.json).

| Candidate | OA graph ms | ptxas graph ms | cuBLAS event ms |
|---|---:|---:|---:|
| Tall FP16 `m_fast` | 2.727 | 2.946 | 2.431 |
| Tall FP16 `morton8` | 2.536 | 2.368 | 2.401 |
| Tall BF16 `m_fast` | 2.653 | 2.932 | 2.292 |
| Tall BF16 `morton8` | 2.458 | 2.303 | 2.181 |

All four cuBLAS outputs passed the FP32 tolerance. Relative L2 versus the OA
output was about `3.98e-6` for FP16, zero for BF16 in this run, and the maximum
absolute errors versus the FP32 reference were `0.00226` and `0.00320`.
cuBLAS was timed with explicit events rather than CUDA Graph capture because
the ctypes call produced an empty graph on this image; the event path is the
valid cuBLAS timing in this record.

## Decision

The next compiler experiment should target fragment/register issue behavior:
jointly search B-fragment ownership/load order, `.reuse` hints, independent
accumulator chains and live ranges while retaining established async-copy,
LDSM address-WAR and HMMA dependency edges. A three/four-stage variant should
be admitted only if register/shared-memory occupancy remains plausible and the
same full-output/canary contract passes. Do not change production scheduling
from these counters alone. The raw JSON remains under `exp/` until the harness
and repeated timing are independently confirmed.
