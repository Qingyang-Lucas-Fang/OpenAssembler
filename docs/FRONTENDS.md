# Compiling your own kernels: PTX, Python, and CUDA C/C++ to SASS

`openassembler compile` takes a kernel in any of three languages and produces a
**`.cubin`** (loadable on the GPU) and a **`.sass`** (the SASS listing, decoded by
NVIDIA's `nvdisasm`). Everything after PTX, including register allocation,
scheduling and instruction encoding, is done by this project's own backend.

| You write | Frontend | Turned into PTX by | SASS generated by |
|---|---|---|---|
| `kernel.ptx` | none | you | **openassembler** |
| `kernel.py` (small numeric subset) | `openassembler/pyfront/` | **openassembler** (from scratch) | **openassembler** |
| `kernel.cu` / `.cpp` / `.cc` | `openassembler/cppfront.py` | NVIDIA's `nvcc --ptx` | **openassembler** |

Be clear about what is and isn't ours: for CUDA C/C++ the C++ parsing and NVVM
optimization are `nvcc`'s (it is already the oracle this project is checked
against). Only the step from PTX to SASS is replaced.

```sh
openassembler compile examples/div_by_const.ptx -o out.cubin --verify   # PTX
openassembler compile examples/vector_add.py    -o out.cubin --verify   # Python
openassembler compile examples/vector_add.cu    -o out.cubin --verify   # CUDA C
# each writes out.cubin AND out.sass
```

## What you need installed

Compiling needs NVIDIA's toolkit once, for the `ptxas`-built ELF container our code
is spliced into, for `nvdisasm` (the `.sass`), and for `nvcc` (CUDA C only). It is
never bundled; `env/fetch_cuda.sh` downloads it. See [REPRODUCING.md](../REPRODUCING.md#c-with-nvidias-toolkit).
Even a Python kernel needs `ptxas` (for the container). `--no-sass` skips only the `nvdisasm` step, and `--base-cubin X` replaces the `ptxas` step if you already have a cubin for the same kernel signature. CUDA C also needs a host C++ compiler (`g++`).

## Options

| Flag | Meaning |
|---|---|
| `-o PATH` | cubin to write (default: next to the source). Anywhere writable; an existing directory gets `<dir>/<name>.cubin`. The `.sass` goes beside it, so give `-o` a `.cubin` name. |
| `--sass PATH` / `--no-sass` | where to put the SASS listing (default: next to the cubin, `.sass`), or skip it |
| `--kernel NAME` | which kernel/function, when the file has several |
| `--opt-level safe\|mined\|sched\|opt` | `safe`: fixed 6-cycle stalls. `mined`: A100-measured latencies. `sched`: + list scheduling. `opt` (default): + 4x loop unrolling, which only applies to a counted `add.u32`/`setp.lt.u32` do-while loop (what the benchmark kernels use); the top-tested `s32` loops pyfront and nvcc emit are left as they are, so for them `opt` equals `sched`. All four are checked bit-exact; see [docs/STATUS.md](STATUS.md) for the speed difference. |
| `--dump-ptx` | print the PTX the frontend produced before compiling it |
| `--verify` | run the result and compare it with the PTX reference interpreter (below) |
| `--arch sm_80` | target. Only `sm_80` has an encoder; anything else stops with "no SASS encoder data for ..." |

## Python (`openassembler.pyfront`)

A decorated function in a normal `.py` file. This is a deliberately small subset in
the spirit of Numba's `@cuda.jit`, not general Python:

```python
from openassembler.pyfront import Array, f32, i32, kernel

@kernel
def saxpy(a: f32, x: Array(f32), y: Array(f32), n: i32):
    i = tid_x() + ctaid_x() * ntid_x()
    if i < n:
        y[i] = a * x[i] + y[i]
```

`tid_x() ctaid_x() ntid_x()` (and `_y`, `_z`) are the thread/block indices; they are
only valid inside a `@kernel`. Calling a `@kernel` function from Python raises: it
is compiled, not run.

**Works.** Each of these is checked three ways in [`tests/test_pyfront_semantics.py`](../tests/test_pyfront_semantics.py): as plain Python, on the PTX interpreter, and as our SASS on the emulator. Parameters `Array(f32)`, `Array(i32)`, `f32`, `i32`; local variables; `+ - *` on `f32` and `i32` (float literals included: `a[i] * 2.0 + 1.5`); unary `-`; comparisons; `if / elif / else`; `and` / `or` as the condition of an `if`; a bare `return` as an early exit (`if i >= n: return`); `for j in range(start, stop[, step])` with a constant step, negative included; `a[i]` reads/writes and `a[i] += x`.
Mixing types is an error, not a silent conversion: `out[i] = 1` into an `f32` array, a float index or bound, and `i32 + f32` are all rejected (write `1.0`).
A worked example with loops and several kernels: [`examples/mlp/kernels.py`](../examples/mlp/kernels.py).

**Rejected, with a message that names the construct** (so nothing is silently wrong):

| Not supported | Why / what to do |
|---|---|
| `while`, `min()`/`max()`/`abs()`, other function calls | not implemented in pyfront |
| `and`/`or` outside an `if` condition (`ok = a < b and ...`) | would need a combined-predicate instruction the backend lacks; put it in the `if` |
| `not x`, `float(i)`, `int(x)`, mixing `i32` with `f32` | the backend has no `not.pred` / `cvt`; pyfront accepts the syntax but compile stops with "our backend can't compile this kernel yet" |
| `x / y` on floats, `i // k`, `i % k` | no divide instruction in the backend yet (CUDA C's `x / 7` *does* work, see below) |
| shared memory, `__syncthreads`, atomics, `f16`/`f64` | not in pyfront (CUDA C can use shared memory, see below) |
| loop variable semantics | `for j in range(...)` leaves `j` equal to the stop value afterwards (Python leaves the last value), and assigning to `j` inside its own loop is rejected |

## CUDA C/C++ (`openassembler.cppfront`)

Mark kernels `extern "C"` so `nvcc` doesn't mangle their names:

```cuda
extern "C" __global__ void vector_add(float* a, float* b, float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = a[i] + b[i];
}
```

Without `extern "C"` the symbol becomes e.g. `_Z7mangledPf`, and `--kernel mangled` will
not match it (the error lists the names that exist; use that one).

Checked end to end against the PTX interpreter (`--verify` bit-exact): `saxpy` with a float scalar,
ReLU via `?:`, integer `& << >> + -`, and integer division by a constant (`nvcc` lowers it to
multiply-high before we see it). **Shared memory with `__syncthreads`** compiles and runs correctly on
the SASS emulator (checked with a 64-thread array reversal), but the PTX reference interpreter cannot model a
barrier across warps, so `--verify` stops with "not verified" (exit 2, the cubin is kept).
Rejected with a clear message today: `sqrtf` (`sqrt.rn.f32`), float division
(`div.rn.f32`), and loops that `nvcc` strength-reduces into pointer increments
(`add.s64` with an immediate), which includes plain `for (...) acc += a[row*n+j]*b[row*n+j]`
dot-product loops. That last one is the most useful thing still missing from the backend.

On macOS `nvcc` runs inside the colima VM, which only sees your home directory. A source
file outside it is compiled from a scratch copy, so a local `#include "x.h"` next to it
will not resolve; keep such projects under `$HOME`.

## What `--verify` proves, and what it doesn't

It runs your compiled kernel on this project's SASS emulator and the same PTX on the
reference interpreter, then diffs every pointer parameter's memory. It is bit-exact
or it fails. To make that work for any signature it has to pick inputs itself:

- every pointer is a buffer of `n` (64) 4-byte elements filled with random `f32` bit patterns, one
  thread per element, a single block of 64 threads (so kernels using `__syncthreads` across warps can't
  be checked: exit code 2, "not verified");
- integer scalars become small values (1..n) and any parameter named `n`, `count`,
  `size`, `len`, `num` or `length` is exactly `n`; floats are random in [-8, 8].

So it will not exercise multi-block grids, kernels that index past `n`, or `f64`/`i64`
buffers. For those, write a check like the multi-CTA one in [`tests/test_pyfront.py`](../tests/test_pyfront.py).
A kernel with the original probe signature `(out, in, k, kf)` uses the older, stricter
probe harness automatically.

Exit codes of `compile --verify`: **0** compiled and bit-exact; **1** compile error, or it compiled but
did not match (the bad `.cubin`/`.sass` are deleted, so they can't be picked up by mistake); **2** compiled
but could not be checked (files kept).

## Running the result on a GPU

`compile` produces the cubin; running *your own* cubin on hardware is not yet a one-line
CLI command (`openassembler gpu run` runs the project's probe corpus). The tested way is
the plan runner used for the MLP example: [`tools/mlp_run.py`](../tools/mlp_run.py) builds a job from
cubins + buffers + launch geometry and runs it on an A100 through Modal, and
[`openassembler/gpu/cuda_driver.py`](../openassembler/gpu/cuda_driver.py) (`run_plan_job`) documents the job format and
works over SSH too. Measured on an A100, both our cubins and `ptxas`'s match a float64
reference; `ptxas` is currently faster on those naive untiled kernels (0.047 ms vs 0.127 ms at
64x128x256x64, 0.40 ms vs 0.92 ms at 128x512x2048x512). See [docs/STATUS.md](STATUS.md).

## Errors you may see

| Message | Meaning |
|---|---|
| `error: NotSupported: ... (line N)` from pyfront | the construct is outside the Python subset above; `N` is the line in your file |
| `our backend can't compile this kernel yet: <ptx op>` | valid PTX, but that instruction isn't implemented in `openassembler/backend/ra.py` |
| `our encoder can't encode this kernel: ...` | the instruction exists but one operand form was never observed in the reverse-engineering corpus (or `--arch` isn't sm_80) |
| `couldn't build the ELF container with ptxas` | toolkit not fetched (macOS: also `colima start`), **or** ptxas rejected the PTX (the message shows ptxas's own error, e.g. a float used as an array index) |
